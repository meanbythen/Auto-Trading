### 2.2 方法

- **静态**：ruff（E4/E7/E9/F/W）、mypy（核心模块严格）、import-linter（三层依赖契约）。
- **供应链**：`pip-audit` 对 `requirements.lock` 与实际解释器各扫一次。
- **性能**：`tests/perf/` 固定数据、固定种子、5 个基准，`PERF_STRICT=1` 严格门禁。
- **报告**：`tools/perf_report.py --latest` 生成环境卡、指标表、趋势与结论。

| PERF-01 | ms | 642.99 / 614.18 / 626.42 | 1.14 / 1.09 / 1.11 | 626.42 | 619.65（中位数；p95 1135 为单次抖动） | ≤ 3000 | 通过（旧基线曾 1.30 失败） |
| PERF-04 | ms | 0.014 / 0.033 / 0.015 | 0.91 / 2.17 / 1.02 | 0.015 | 0.018 | ≤ 2000 | 通过（5 ms 噪声内，只判绝对阈值） |
| PERF-06 | ms | 0.310 / 0.407 / 0.362 | 1.07 / 1.40 / 1.25 | 0.362 | 0.317 | ≤ 8000 | 通过（5 ms 噪声内，只判绝对阈值） |
| PERF-07 | bars/s | 3418.5 / 3419.3 / 3581.0 | 0.947 / 0.947 / 0.992 | 3419.3 | 3606.1 | ≥ 1500 | 通过（旧下限 0.8，新下限 0.85） |
| PERF-09 | ms | 21.30 / 22.75 / 23.65 | 1.04 / 1.11 / 1.15 | 22.75 | 21.44 | ≤ 200 | 通过 |

解读：

1. **PERF-01（冷启动导入 `src.ui.app`）** 按 lock 对齐（pandas 2.3.3、Pillow 13.0.0）后为 614–643 ms，稳定落在 1.2 相对门禁内；此前 736 ms / 1.30 的失败**可归因于环境漂移，而非交易代码回归**。本轮还观测到单次 926 ms 的抖动（5 次中仅 1 次，p95 会被它拉到 1.48），因此冷启动改为 5 次取中位数，严格复核 619.65 ms。
2. **PERF-07（回测吞吐）** 三次为 3418–3581 bars/s，比值 0.947–0.992，波动收敛到约 5%；吞吐改为 3 次取中位数（p95 在 3 个样本里正好是最好那次，会偏乐观），门禁下限提到 0.85、绝对阈值提到 1500 bars/s 后仍有余量。
3. **PERF-04/06** 是亚毫秒指标，三次差异均在 5 ms 噪声下限内，只按绝对阈值判定；表中比值仅供参考。
4. **PERF-09** 22.75 ms，为基线的 1.11 倍，仍有约 9 倍阈值余量。
5. 结论：**冻结依赖 + 三次采样取中位数后，性能门禁已可重复**。53.7.22 升 pandas 3.0.6 后哈希变为 `de4bd406a0ca`，新基线已重设；旧基线备份在 `build/perf/baseline-before-53.7.22.json`（不进 Git）。

## 8. 缺陷清单

### DEF-01 [S3 / P2] 性能报告把"相对基线超限"误写成"超过绝对阈值"

- **版本/环境**：53.7.7，Windows 11 / Python 3.12.10。
- **前置条件**：存在基线，某用例仅相对比值超 1.2、但绝对值远低于阈值。
- **复现步骤**：
  1. `python -m pytest -m perf tests/perf`（本轮 PERF-01 即此情况）；
  2. `python tools/perf_report.py --latest`；
  3. 查看"## 5. 结论"。
- **实际结果**：`PERF-01：超过绝对阈值 3,000.0 ms；基线 564.62 ms，比值 1.30`；而 PERF-01 实测 735.89 ms，**并未超过 3000 ms**。
- **预期结果**：只列出真正失败的原因，例如"基线 564.62 ms，比值 1.30（超过 1.2 相对门禁）"。
- **证据**：`tools/perf_report.py` 结论段只要 `threshold` 非空就拼接"超过绝对阈值"，未判断 `threshold_ok`。
- **影响**：报告误导评审，掩盖真实原因（相对回归），可能导致错误的性能优化方向。
- **规避方案**：人工对照"指标总表"的 p95 与阈值列。
- **根因分类**：规则实现错 + 测试缺失（`tests/test_perf_report.py` 未覆盖"仅相对超限"场景）。
- **状态**：**53.7.9 已修复**。`evaluate_case` 新增 `threshold_ok`/`ratio_ok`，结论只列真实失败项并标注"超过 1.2 / 低于 0.85 相对门禁"（0.85 为 53.7.10 起吞吐下限，53.7.9 时为 0.8）；新增 4 条单测（仅相对超限含严格模式退出码、仅阈值超限、吞吐回归、吞吐提升），53.7.10 再补 1 条"吞吐取中位数"，该文件共 11 项全部通过。

### DEF-02 [S2 / P1] 依赖存在已知漏洞，`pip-audit` 门禁不通过

- **证据**：`pip-audit -r requirements.lock` → 76 条 / Pillow 11.3.0；`pip-audit`（当前环境）→ 72 条 / 6 个包。

- **规避方案**：限制程序只访问受信接口；不打开外部图片/PDF。
- **根因分类**：外部依赖 + 缺少定期审计流程。
- **状态**：**53.7.10 已修复**。Pillow → 13.0.0（先隔离 venv 验证），certifi → 2026.10.18、pypdf → 6.21.4、soupsieve → 4.0.0 钉进 lock，pip/setuptools 升级；lock 与环境两次 `pip-audit` 均 0 条；CI 已加入依赖审计步骤。

### DEF-03 [S2 / P1] 本地环境与 `requirements.lock` 漂移，且依赖哈希无法发现

### DEF-06 [S3 / P2] 性能基准跨轮波动大，单轮门禁不可靠

## 11. 怎么做软件测试、有没有专用集成工具

### 11.1 六步闭环（本项目已按此落地）

1. **定计划**：明确测什么、不测什么、什么算通过 → `docs/软件测试方案.md` 第 1、9 章。
2. **写用例**：每条用例必须有编号、前置、步骤、**预期结果**、自动化标记 → `docs/软件测试用例.md`。
3. **备环境**：固定依赖、固定时钟、临时工作区，不碰真实 `data/` 与密钥 → `.venv` + `tmp_path`。
4. **执行**：单元 → 集成 → 系统 → 人工，分层执行，失败先定位再改代码。
5. **管缺陷**：按 S0~S4 分级，S0/S1 必修且必须补回归用例 → 本报告第 8 章模板。
6. **出报告 + 回归**：每次发版跑同一套门禁，覆盖率只升不降 → 本报告与 `CHANGELOG.md`。

关键原则：**测试是找错，不是证明无错**；有效输入与无效输入同等重要；缺陷聚集的地方加密回归；固定用例之外每版补充变异输入，避免"杀虫剂悖论"。

### 11.2 三层执行节奏

| 时机 | 跑什么 | 目标时长 |
|---|---|---|
| 提交前 | `ruff` + 相关单测 | < 5 分钟 |
| PR | `ruff` + `mypy` + `lint-imports` + `pip-audit` + 全量 `pytest --cov` | < 15 分钟 |
| 夜间/发版前 | 性能基准 + 长稳 + 打包冒烟 + 人工演练 | 按需 |

### 11.4 本项目可直接复制的最小命令集

```powershell
# 1) 日常回归（默认排除 perf/soak）

.\.venv\Scripts\python.exe -m mypy
.\.venv\Scripts\lint-imports.exe

# 4) 依赖审计

# 5) 性能门禁 + 报告
$env:PERF_STRICT="1"; .\.venv\Scripts\python.exe -m pytest -m perf tests\perf
.\.venv\Scripts\python.exe tools\perf_report.py --latest

# 6) 长稳（24h，按检查表执行）
.\.venv\Scripts\python.exe tools\perf_soak.py --hours 24 --symbols 10
```
