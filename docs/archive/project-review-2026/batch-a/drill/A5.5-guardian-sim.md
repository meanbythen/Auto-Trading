## 1. 演练目的

对应 [spec.md](../spec.md) 第 9.5 节，验证守护进程的两次关键判断：

1. **主进程真的没了** → 交易时段内应接管平仓，且只平一次。
2. **主进程还活着（只是心跳停了）** → 只能告警，**绝不**下单（避免同账号互踢）。

同时覆盖误动作边界：心跳正常、非交易时段、无持仓、CTP 未配齐时都不能平仓；守护重启后不能重复平仓。

## 2. 方法

用真实子系统构造场景，只把两处外部副作用换成探针：

| 环节 | 本次做法 |
|---|---|
| 主进程存活 / 死亡 | 真实子进程 `python -c "import time; time.sleep(60)"` 启动后 `terminate()`，等 PID 真正消失再断言 |
| PID 存活判断 | 真实 `Guardian.pid_alive()`（Windows `OpenProcess` + `GetExitCodeProcess`） |
| 心跳新鲜度 | 真实 `data/bot_state.json`，改写 `heartbeat_at` 到指定分钟前 |
| 交易时段 | 真实 `GuardianConfig.sessions` 解析；场景 4 用「当前时刻 +2 小时」构造窗口，确保断言时确实在时段外 |
| 动作落盘 / 告警 | 真实 `data/guardian_actions.jsonl` 与 `emit_alert` 输出到独立临时目录，不污染仓库 `data/` |
| **真实平仓** | 换成假 `flatten_fn`，只记录被要求平的合约列表 |

每个场景用独立的临时工作目录，避免上一场景的状态文件互相影响。演练脚本为工作区外的临时文件 `%TEMP%\a5_guardian_drill.py`，不随仓库提交。

## 4. 本次覆盖到的设计点

- 五个条件（有仓 + 心跳过期 + 主进程 PID 不存在 + 交易时段 + CTP 齐全）**必须同时满足**才会平仓；缺任意一条只返回对应原因。
- `stale_main`（PID 还在）与 `flattened`（真接管）走不同分支：前者只进内存去重表 `_alerted`，不影响后续进程真死时的接管 —— 场景 2 连跑两次仍保持可接管状态。
- 平仓前先写 `data/guardian_actions.jsonl`，用 `run_id` 落盘去重；守护自己重启后读回该文件，场景 7 未产生第二笔平仓。
- 默认关闭是硬约束：未改配置时 CLI 直接退出，不进入轮询。
