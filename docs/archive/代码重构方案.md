期货自动化交易程序：解耦设计思想 + 全模块集成规划
前提：保障现有功能齐全
目标：低耦合、可单独替换、可并行回测、实盘隔离、方便迭代、方便新增策略/指标/柜台
核心原则：数据、信号、风控、下单、日志、存储、监控完全解耦，依赖倒置，策略只负责输出信号，不碰任何交易接口、风控、仓位管理底层
注意不要犯“零、常见踩坑提醒（量化策略重构特别容易犯）”所提到的问题

〇、常见踩坑提醒（量化策略重构特别容易犯）
1. 过度解耦：拆到颗粒度爆炸，一个简单判断拆 3 个类，可读性下降；你这个策略，上面 6 个分层足够，不要再细分。
2. 上下文膨胀：ctx 里塞满所有临时变量；ctx 只放原始数据，计算结果进 features 字典。
3. 跨模块共享可变对象：比如把 list 直接传给多个模块，一个模块修改，其他模块被动变更；全部传只读副本。
4. 把业务判断放进执行器：执行器只负责 “怎么做”，不负责 “要不要做”。

一、顶层解耦思想（核心设计理念）
1. 分层边界（单向依赖，禁止反向调用）
【接入层】 ← 【数据层】 ← 【策略层】 ← 【信号层】 ← 【执行层】 ← 【风控层】 ← 【柜台网关层】
监控告警层、持久化存储层、配置层 → 全局公共组件，所有层只读，不反向依赖业务逻辑
✅ 规则：
● 上层可以调用下层抽象接口，下层绝对不能感知上层实现
● 策略模块只输出标准化信号，不直接发单、不查账户、不写日志硬编码
● 所有外部依赖（CTP、天勤、同花顺、CSV回测数据）都封装抽象接口，切换数据源/柜台不用改策略代码
● 回测、仿真、实盘三套环境共用同一套策略代码，由配置注入不同适配器
2. 核心解耦手段
1. 接口抽象（Adapter适配器模式）：定义统一抽象基类，CTP网关、回测网关、仿真网关实现同一个接口；切换柜台只换适配器
2. 事件驱动（EventBus事件总线）：模块之间通过事件通信，模块之间无直接对象引用，是vnpy体系的基石
3. 数据契约（DTO标准化报文）：Tick、K线、订单、成交、信号、资金都定义固定结构，所有模块只认标准结构体，不识别内部字段细节
4. 配置驱动：所有参数（品种、ATR参数、手数、风控阈值、周期、开关）放配置文件，代码无硬编码
5. 职责单一原则：一个模块只做一件事；风控模块只做拦截，不生成信号；策略只算信号，不负责下单
3. 边界隔离清单（哪些必须拆开）
❌ 禁止写在同一个类里：K线合成 + 指标计算 + 开仓判断 + 发单 + 风控判断 + 日志输出
✅ 拆分：行情接收 → K线聚合 → 指标计算 → 策略信号生成 → 仓位管理器 → 风控校验 → 订单路由 → 成交回调 → 结果落地

二、完整功能模块拆分（独立可插拔模块）
模块0：全局配置 & 环境管理模块（基础公共模块）
职责：
● 加载yaml/json配置：品种列表、交易周期、手续费、保证金、策略参数、风控阈值、账户信息、日志等级、环境标记 backtest/simulation/real
● 环境隔离：实盘开关、是否允许下单、是否只读行情
● 动态配置热加载（可选）
输出：全局Config对象，只读；所有模块通过依赖注入拿到配置，不直接读文件
解耦点：策略不需要写死参数，同一套策略实例可以多品种、多参数并行运行
模块1：网关接入适配器层（行情+交易通道）
抽象基类定义方法：订阅行情、发单、撤单、查询持仓、查询资金
实现类：
1. CTP网关（实盘）
2. 天勤Tqsdk网关（行情/仿真）
3. 回测回放网关（本地csv/parquet tick/k线回放）
4. 模拟仿真网关（内存撮合，用于本地仿真）
输出标准事件：TickEvent、OrderEvent、TradeEvent、PositionEvent、AccountEvent
解耦点：策略层完全不知道底层是CTP还是回测回放，报文结构一致
模块2：数据处理层（行情清洗、K线聚合、特征工程）
子模块：
● 行情清洗：去重、过滤异常tick、时间戳对齐、涨跌停标记
● K线合成器：Tick → 1min/3min/15min K线；支持多周期合成；支持跳空修复
● 特征计算模块（独立！和策略解耦）：ATR、ADX、MA、MACD、VA成交量分布、波动率、价差等指标
  ○ 指标输入：标准K线序列；输出：指标值序列
  ○ 指标做成独立函数/类，可单独单元测试，可给回测、实盘、可视化共用
● 数据缓存：K线缓存池、tick环形队列，限制内存，防止爆内存
● 数据持久化：tick/k线写入parquet/数据库（可选）
重点：指标计算和策略逻辑分离，多个策略可以复用同一套ATR、VA指标，指标改动不影响策略业务
模块3：事件总线 EventBus（模块通信中枢）
核心组件，所有模块不直接互相调用，只发布/订阅事件
事件类型清单：
● Tick事件、BarK线事件
● 指标就绪事件
● 策略信号事件（SignalEvent）
● 订单请求事件（OrderRequestEvent）
● 订单回报、成交回报事件
● 风控拦截事件
● 告警事件
特点：同步/异步可选；实盘用轻量同步事件，回测可单线程顺序事件驱动保证时序正确
模块4：策略内核层（纯信号生成层，最干净的一层）
这是整个系统里最核心、最应该轻量化的模块
职责：接收K线+指标数据，输出标准化信号，不访问账户、不发单、不查持仓、不风控
信号标准结构 Signal DTO：
{
  "symbol": "fu2601",
  "direction": "long/short/close/closelong/closeshort",
  "price": 1850.0,
  "volume": 1,
  "signal_time": 1731223344,
  "strategy_id": "cta_atr_adx_01",
  "signal_type": "open/close",
  "reason": "adx>25 + price breakout upper"
}
子模块：
1. 策略基类：统一接口 on_bar()，接收bar，返回信号列表
2. 策略实现实例：ADX+ATR过滤CTA、CIS简化版、多因子、突破策略等
3. 策略管理器：多策略实例调度，同一个品种挂载多个策略，信号合并
4. 信号去重器：防止同一K线反复触发重复开仓信号（防闪信号、毛刺）
解耦关键点：策略只回答“我想干什么”，无权决定能不能下单、下多少手；仓位、手数交给独立仓位管理器
模块5：仓位&资金管理模块（独立于策略）
很多人容易把仓位写死在策略里，这是强耦合大坑，必须单独拆
职责：
● 维护目标持仓表、当前实际持仓、可用资金
● ATR动态仓位计算、固定手数、固定风险比例（1%账户风险）、金字塔加减仓规则
● 信号转换：把策略的“开多信号”翻译成目标手数
● 目标持仓和实际持仓对比，生成调仓指令（需要开多少、平多少）
输入：策略Signal、账户资金、当前持仓、ATR波动率
输出：调仓请求（OrderRequest）交给风控模块
✅ 好处：同一个突破策略，可以切换固定手数 / 1%风险仓位模型，不用改策略代码
模块6：前置风控模块（拦截器，在发单之前）
独立拦截器链，链式校验，任意一条不满足直接拦截，返回风控事件
风控检查项：
● 总资金上限、单品种最大持仓手数限制
● 单日最大亏损、单日最大开仓次数
● 滑点阈值、涨跌停禁止开仓
● 同方向重复开仓限制、锁仓开关
● 最大挂单数量、撤单频率限制
● 实盘开关总闸（紧急一键停单）
● 时间风控：只在日内交易时段允许下单，收盘前强制平仓
设计：责任链模式，可以自由增删风控规则，开关控制是否启用某条风控，不改动其他代码
模块7：订单执行&路由模块（执行器）
接收风控放行后的订单请求，负责订单生命周期管理
子模块：
● 订单拆分：大单拆小单、时间切片算法（TWAP）
● 限价单/市价单转换、滑点模拟（回测）
● 订单状态跟踪：已报、已成、拒单、撤单、超时未成交处理
● 撤单重试逻辑、超时自动撤单
● 订单路由：多账户分发、不同品种路由到不同网关
输出：OrderEvent、TradeEvent，发回事件总线
模块8：成交后处理 & 绩效统计模块
接收成交回报，做后处理：
● 更新本地持仓、资金快照
● 每笔成交记录入库：信号、下单时间、成交时间、滑点、盈亏
● 绩效指标实时计算：胜率、盈亏比、最大回撤、夏普、总盈亏、连续亏损
● 交易日志结构化输出
模块9：持久化存储模块
职责：统一数据落盘，其他模块只调用存储接口，不关心数据库
存储对象：
● Tick、K线Bar
● 信号记录、委托单、成交记录
● 绩效快照、日志
存储适配器：Parquet（行情）、SQLite/MySQL（交易记录）、Redis（实时缓存持仓资金）
支持切换存储后端，比如本地回测用parquet，实盘用数据库
模块10：监控告警 & 可视化模块
● 实时监控：连接状态、行情延迟、策略心跳、风控拦截日志、资金曲线
● 告警通道：日志、钉钉/企业微信推送、本地弹窗
● 可视化：K线回放、信号标记、资金曲线、回撤曲线（回测/实盘共用一套绘图接口）
● 健康检查：网关断线自动重连、策略心跳检测，策略卡死告警
模块11：回测框架（独立运行环境，复用全部上层模块）
回测本质：把网关适配器替换成历史回放网关，事件总线顺序驱动
● 回测引擎：时间轴推进，按历史tick时序回放
● 滑点模型、手续费模型、保证金模型独立配置
● 并行回测调度：多参数网格搜索（参数优化）
● 注意：回测和实盘复用同一策略代码、指标代码、风控代码，只替换底层适配器

三、模块数据流完整链路（实盘一条交易链路）
1. 网关 → TickEvent → 事件总线
2. 数据层订阅Tick → K线合成 + 指标计算 → BarEvent（带指标）
3. 策略订阅BarEvent → 计算逻辑 → 输出SignalEvent
4. 仓位管理器订阅Signal → 结合资金持仓 → 生成调仓OrderRequest
5. 风控链订阅OrderRequest → 逐项校验
  ○ 校验通过：放行给订单执行器
  ○ 校验失败：抛出风控拦截事件，写入日志告警，终止流程
6. 订单执行器 → 下发给CTP网关 → 交易所
7. 交易所回报（Order/Trade）→ 网关推送事件总线
8. 仓位管理器、绩效模块、存储模块同时订阅成交回报，更新状态、记录绩效、落库
9. 监控模块订阅全部事件，展示状态、触发告警
回测链路：完全一致，只是网关换成历史回放，时间由回测引擎驱动，没有外部CTPIO

四、依赖注入与集成方案（工程落地）
推荐工程目录结构（Python/vnpy风格）
Auto-Trading/
├── config/                # 配置yaml
├── adapters/              # 网关适配器：ctp、tq、backtest_player
├── eventbus/              # 事件总线、事件DTO定义
├── data_layer/            # tick清洗、bar合成、指标库
│   └── indicators/        # 独立指标（ATR/ADX/VA）
├── strategy/              # 策略基类 + 各个策略实现
│   └── strategy_manager.py
├── position_manager.py    # 仓位资金管理
├── risk/                  # 风控规则链
├── execution/             # 订单执行、拆单、超时管理
├── recorder/              # 存储持久化
├── performance/           # 绩效计算
├── monitor/               # 告警、可视化
├── backtest_engine.py     # 回测引擎
├── main_real.py           # 实盘入口
└── main_backtest.py       # 回测入口
集成规则
1. 所有模块通过构造函数注入依赖（eventbus、config），不全局import单例
2. 单元测试：策略、指标、风控都可以单独构造测试用例，mock行情事件，不需要启动CTP
3. 多实例并行：同一个策略，不同品种、不同参数，独立实例，互不干扰
4. 热插拔：新增一个策略，只需要继承策略基类，注册到策略管理器，不需要改动网关、风控、下单代码

五、关键避坑点（解耦最容易踩的坑）
1. ❌ 策略里直接读取 self.pos 持仓变量
✅ 策略只输出信号，持仓由仓位管理器统一维护，策略不感知实时持仓
2. ❌ 回测一套代码，实盘重写一套
✅ 适配器隔离，业务层完全复用
3. ❌ 风控写在策略if判断里面
✅ 风控独立拦截链，实盘可以一键开启/关闭，回测也复用同样风控规则
4. ❌ 指标硬编码嵌在策略循环里
✅ 指标库独立，指标先算好随Bar事件一起下发，策略只读取指标值
5. ❌ 全局变量传递资金、持仓
✅ 全部通过事件传递，状态收敛在仓位管理器，不使用全局共享状态

六、扩展能力规划（后续迭代）

详细施工说明见 [扩展能力规划.md](../扩展能力规划.md)。下面五条 **18.23.0 都还没做完**，不是已经交付的功能。

● CIS模式：CIS的一致性筛选、分仓逻辑放在仓位管理器，而不是策略内
● 多账户：网关适配器支持多账户，路由模块分发订单

● 分布式：事件总线改成消息队列（redis/mq），行情服务、策略服务、执行服务拆成独立进程

没有把整个工程改名叫 `trading_system/`，避免界面、测试、打包路径全断。分层落在现有 `src/` 里，策略文件不拆碎。
