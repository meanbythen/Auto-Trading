# 评估盲区修复与审计脚本实施计划

## Context

当前评估体系已覆盖基础指标、滑点和参数扰动，但优化流程存在口径混杂：冠军参数在最后训练段复跑形成 `best_result`，压力和扰动却使用优化输入 `cfg`、完整请求区间，扰动基准 PF 又来自训练段。与此同时，旧结果、缺失评估、样本外无交易、压力未执行、盈利集中和 ADX 缺失等问题需要人工逐项打开文件才能发现。

用户已确认本次采用“**口径修复＋审计脚本**”：修正优化评估的参数与区间口径，并增加一个只读检查工具；不扩展为组合回测、完整 UI 或新的策略门槛体系。

## 一、修复优化评估口径

### 修改 `src/backtest/optimizer.py`

1. 保留现有 `best_result`：继续表示冠军参数在最后训练段的复跑结果，`best_limits` 仍取其 `params_snapshot`，避免改变训练快照含义。
2. 在 `best_params` 已产生且评估启用时，新增独立 `eval_result`：
   - 使用 `eval_cfg = _apply_params(cfg, best_params, engine_name)`；
   - 使用本次优化请求的 `symbol/start_date/end_date/engine_name` 在完整区间复跑；
   - 不传入训练段 `bars_signal/bars_trail`。
3. 将以下输入统一到 `eval_result/eval_cfg`：
   - `evaluate_backtest(eval_result)`；
   - 压力样本门槛取全区间成交笔数；
   - `run_slippage_stress(eval_cfg, ...同一区间)`；
   - `run_perturbation(eval_cfg, ...同一区间)`；
   - 扰动 `base_pf=eval_result.performance.profit_factor`，不再使用 `train_perf`。
4. 可抽出一个带可选 runner 的内部辅助函数，便于用假回测结果验证配置、日期和 PF；生产调用仍复用现有 `run_backtest`、滑点和扰动函数。
5. 不改变训练评分、冠军选择、holdout、滚动前进、多品种验收的顺序和规则，也不改变 `best_performance/train_performance/holdout_performance` 的含义。
6. 新增一次全区间回测；滑点仍额外运行一次，扰动仍最多四个点。压力是否执行可能因样本口径从训练段改为全区间而变化，这是预期行为。
7. 全区间复跑失败时返回带 `skipped` 原因的评估报告，不伪造通过：
   - `evaluation_ok=false`；
   - `gate_on_optimize=true` 时 `accepted=false`，追加“评估未完成，不写入”；
   - 门禁关闭时保留旧验收结果，但保留失败原因供审计。
8. 评估为 `watch` 时维持当前行为；评估为 `reject` 时继续按 `gate_on_optimize` 拦截。

## 二、新增只读审计模块

### 新建 `src/backtest/audit.py`

模块只接收已经读取的字典，不访问行情、不写文件、不导入回测引擎。建议接口：

```python
def audit_results(
    backtest: dict[str, Any],
    optimize: dict[str, Any],
    config: dict[str, Any],
) -> AuditReport: ...

def format_audit_text(report: AuditReport) -> str: ...
```

数据结构：

- `AuditFinding`：`source/code/severity/message/details`。
- `AuditReport`：保存 findings、关键计算指标、计数和 `to_dict()`。
- 严重级别：
  - `critical`：已有明确红线、红线结果仍 `accepted=true`，或其他交付前必须处理的矛盾；
  - `warning`：证据缺失或启发式异常，必须人工复核但不直接否决；
  - `info`：事实、指标和普通 `skip` 明细。

### 审计项目

| 检查 | 实现口径 | 级别原则 |
|---|---|---|
| 旧结果/缺评估 | `evaluation` 为空、报告级 `skipped` 非空；优化同时 `accepted=true` 时突出提示 | warning；明确红线仍 accepted 时 critical |
| 评估明细 | 逐项展开 `checks`，保留实际值、门槛和 note；`fail/watch/skip` 不静默 | fail→critical，watch→warning，普通 skip→info |
| 优化门禁冲突 | `accepted=true` 且 `evaluation_ok=false` 或评估结论为 reject | critical，提示核查当时门禁，禁止直接写入 |
| 检验段证据 | holdout 零笔；0<笔数<30；PF 低于当前配置门槛 | 零笔/小样本 warning；低 PF 且仍 accepted 时 critical |
| 压力证据 | 当前配置启用评估和压力，且对应结果达到 `stress_min_trades`，但滑点/扰动缺失、有 error 或对应 check 为 skip | warning；已执行后的压力红线由 checks 升 critical |
| 盈利集中度 | 从 `backtest.trades` 计算最大盈利笔占总正盈利比例、剔除盈利前五笔后的净盈亏 | 成交≥30且 top1>50%，或至少5笔盈利且剔除后净盈亏≤0，warning |
| ADX 覆盖率 | 非空 `adx_at_entry` 笔数÷成交笔数；ADX=0 是有效值 | 成交≥30且覆盖率<80%，warning |
| 当前配置可比性 | 当前 `strategy.engine/trade.symbol` 与回测快照、优化结果的 engine/symbol 对比；仅去空格和忽略大小写，不猜连续合约别名 | 不一致 warning，提示不能直接互为样本外证明 |
| 数据区间完整性 | 回测 `params_snapshot`、优化 `best_limits` 的 `data_from/data_to`；优化该快照仍明确为训练段 | 缺失 warning |
| 无亏损笔 PF=99 | 有盈利、无亏损且 PF=99 的绩效块 | warning，说明这是程序占位值，不是可持续高 PF |

30 笔、50%、80% 仅作为人工复核提示线，在文本和 JSON 中注明“非统计显著性判断”。扰动 `ok=false/cliff=true` 不应当作执行失败；只有 `error`、无有效点或 skip 才属于证据缺失。

## 三、新增命令行检查脚本

### 新建 `tools/audit_evaluation.py`

采用 `tools/run_backtest.py` 的项目根目录导入方式，但直接用 `json` 和 `yaml.safe_load` 读取文件，**不调用会创建目录或复制模板的 `load_config()`**。

默认读取：

- `data/backtest_last.json`；
- `data/optimize_last.json`；
- `config/config.yaml`。

参数：

- `--root PATH`：默认脚本推导出的项目根目录；
- `--json`：标准输出结构化报告，便于后续自动化；
- `--strict`：发现 critical 返回 1。

退出码：

- 默认成功完成审计即返回 0，即使存在 warning/critical；
- `--strict` 且存在 critical 返回 1；
- 文件缺失、JSON/YAML 解析失败、根节点不是字典或参数错误返回 2，错误写 stderr。

使用示例：

```powershell
python tools\audit_evaluation.py
python tools\audit_evaluation.py --root "D:\Auto-Trading" --json
python tools\audit_evaluation.py --strict
```

文本输出包含严重级别统计、来源、检查代码、原因和人工复核说明；脚本不重跑回测、不修改配置和结果文件。

## 四、测试

### 新建 `tests/test_audit.py`

使用合成字典和 `tmp_path`，覆盖：

- 旧结果、空评估、skipped、fail/watch/skip 展开；
- accepted 与评估红线冲突；
- holdout 零笔、小样本、低 PF；
- 压力缺失、执行 error、正常 cliff 不被误判为执行失败；
- top1/top5 手算结果、样本不足不触发集中度提示；
- ADX=0 有效及覆盖率边界；
- engine/symbol 可比性和缺失区间；
- PF=99 提示；
- CLI 文本、JSON、退出码 0/1/2，且运行前后输入文件内容不变。

### 扩充 `tests/test_optimizer_holdout.py`

用假 runner/合成 `BacktestResult` 验证：

- 全区间评估收到请求日期，且没有误用训练段 bars；
- `best_params` 已应用到正确策略或公共配置小节，原 cfg 未被修改；
- 滑点和扰动收到相同冠军配置与区间；
- 扰动基准 PF 来自全区间结果，压力样本门槛也看全区间成交；
- 训练段 `best_limits` 不被全区间结果覆盖；
- 旧 holdout/walk/cross 判定不变，门禁开关和复跑失败行为符合设计。

- 组合级相关性、保证金和同时回撤引擎；
- 全参数曲面、多参数联合扰动或蒙特卡洛成交模拟；
- 自动调门槛、自动改参数或自动停开策略；
- 新的统计显著性/多重检验模型；
- 审计结果 UI、完整权益持久化和检验段独立评分体系。
