项目审阅报告（44.0.1）
总体状态：902 项测试全部通过，功能链路完整（CTP + 同花顺 GUI 双通道、回测/交叉测试/优化/复盘/账户分析）。但代码规模已出现明显的可维护性瓶颈。

一、架构问题（高优先级）
问题	位置	影响
上帝类：GUI 主窗口	app.py 9881 行、200+ 方法	任何 UI 改动都要在巨型类里翻找，回归风险高，无法并行开发
上帝类：交易总控	runner.py 2562 行、60+ 方法	登录、风控、下单、清仓、审计、账户同步全在一个类里，职责边界模糊
回测直接改策略私有状态	engine.py:926、runner.py:1919 访问 strategy._last_entry_bar / _signaled_bar	破坏封装，策略内部结构变动会 silently  break 回测和实盘
策略基类不统一	TrendStrategyBase 与独立 evaluate 实现并存	新增策略时无所适从，公共逻辑（信号标记、持仓管理）重复或缺失
二、代码质量问题（中优先级）
● 模块级全局副作用：gui_trader.py:30 pyautogui.FAILSAFE = False 在 import 时修改全局状态，影响所有使用 pyautogui 的模块。
● 密码写入进程环境：config_loader.py:183 把密码同步到 os.environ，方便但扩大了泄露面（子进程、崩溃转储）。
● 超大文件集中：optimizer.py 2227 行、config_tab.py 1652 行、picker.py 1617 行、engine.py 1424 行，均需要拆分。
● print 与 logger 混用：导出/质检脚本里仍有 print()，虽然多为 CLI 入口，但建议统一。
三、性能与资源（待量化）
目前未做 profiling，但结构上有明显风险点：
● KlineProvider.fetch 在 _execute 平仓路径里被再次调用（runner.py:1854），可能引入额外网络/磁盘 IO。
● app.py 的 _refresh_status_cards 在 800ms 定时器里做大量字符串拼接和配置读取，窗口开着就持续消耗 CPU。
● 建议先接 cProfile / py-spy 跑一遍常驻 + 回测，再决定优化点。
四、安全与可靠性
● GUI 下单的 BlockInput 有 pytest 防护（gui_trader.py:45），但生产环境真锁鼠标，需确保异常路径一定 release_pointer_after_order。
● 委托意图文件（crash recovery）机制完整，但 _write_order_intent / _clear_order_intent 与 _apply_fill_accounting 分散在 _execute 多个分支，建议收敛为上下文管理器或装饰器，减少漏清风险。
五、工程化缺口
● requirements.txt 只有下限版本，没有锁定文件，重建环境可能拉到不兼容版本。
● 无 CI（GitHub Actions / 本地 pre-commit），902 个测试靠手动跑。
● 无类型检查（mypy/pyright）和 lint（ruff/flake8）配置，代码风格靠自觉。

建议优化路线
第一阶段：解耦与拆分（1-2 周）
1. 把 app.py 按页签拆成 ui/run_tab.py、ui/backtest_tab.py、ui/optimize_tab.py 等，主窗口只负责导航和状态共享。
2. 把 runner.py 拆成 login_flow.py、order_executor.py、flatten_manager.py、session_audit.py，TradingBot 退化为协调者。
3. 统一策略基类：把 _signaled_bar、_last_entry_bar 提升为公共接口或基类属性，回测和实盘通过公开方法读写。
第二阶段：性能与可靠性
4. 对常驻扫描和回测做 profiling，定位真实热点（K 线重建、指标计算、UI 刷新）。
5. 把下单意图的写/清改成上下文管理器，确保异常安全。
第三阶段：工程化
6. 加 requirements.lock、pre-commit（ruff + mypy）、GitHub Actions 跑测试。
7. 把 print 统一为 loguru，CLI 入口除外。
